## Eight devices without changing the four-study update

Use ordinary replicated PJRT multiprocessing, **not SPMD**. Acquire devices only inside the launched worker. Assert TPU, world size eight, expected addressable topology, no CUDA, all ranks' successful startup, and matching initialization tensor hashes. Each rank has static input **`[1,16,8,1,224,224]`**, original slice/series masks and ten series descriptors. Ranks 0/1 receive the two reference draws, ranks 2/3 the two report draws; ranks 4–7 receive zero pixels/descriptors with every supervision/slice/series mask false. Padding ranks participate in every collective and optimizer step but add no sample/target exposure. The existing fixed-shape model and pooling produce defined zero-masked features. This proposal reduces per-rank activation pressure; real HBM use remains a pilot result. [Fixed-shape encoder](../../src/rsna_knee/full_backbone.py), [pooling](../../src/rsna_knee/feature_pooling.py).

For update `t`, let `N[r,t]` be rank r's sum of supervised BCE entries and let `D[t]` be the supervised-entry count across the four real studies, computed and validated on CPU from frozen masks. Give every rank the same scalar tensor `D[t] > 0`. Backpropagate:

```text
local_loss[r,t] = 8 * N[r,t] / D[t]
XLA mean-reduced gradient = gradient(sum_r N[r,t] / D[t])
```

Thus the update preserves the original combined-entry mean. Averaging each replica's locally normalized BCE would change label weighting; treating all eight ranks as real would change the batch. Use fixed-shape BCE masking, including replacement of absent NaN targets before BCE. Freeze a CPU algebra/gradient equivalence check against the original four-study masked loss, including unequal masks and four empty padding ranks, before TPU admission. This distributed formulation is a proposed implementation, not an existing admitted trainer capability.

The exact **v2.8.0** source tag resolves to **`d517649bdef6ab0519c30c704bde8779c8216502`**. Its `xm.optimizer_step` calls `reduce_gradients`, which sums gradients with scale `1/world_size`; its default barrier is **false**. Explicitly execute **`torch_xla.sync(wait=True)`** before timing completion. `torch_xla.launch` defaults to spawn-based replicated execution and rejects SPMD. Capture actual installed XLA version/git revision; matching version strings alone do not prove wheel/source identity. [Pinned optimizer source](https://github.com/pytorch/xla/blob/d517649bdef6ab0519c30c704bde8779c8216502/torch_xla/core/xla_model.py), [pinned launch/sync source](https://github.com/pytorch/xla/blob/d517649bdef6ab0519c30c704bde8779c8216502/torch_xla/torch_xla.py).

Set **`torch_xla.backends.set_mat_mul_precision('highest')` once per fresh worker**, before computation, and verify it with the corresponding getter. Reject BF16/downcast environment settings and autocast. FP32 storage alone does not ensure ordinary FP32 arithmetic: the pinned backend describes default TPU FP32 matmul/convolution as downcasting to BF16; `highest` uses six passes with approximately 22-bit precision. Even that mode can differ in the last bits from CPU. Do not silently use the faster default to improve a benchmark. [Pinned precision API](https://github.com/pytorch/xla/blob/d517649bdef6ab0519c30c704bde8779c8216502/torch_xla/backends/__init__.py), [official precision tutorial](https://docs.pytorch.org/xla/release/r2.8/tutorials/precision_tutorial.html).

1. **One CPU preparation allocation:** verify every selected real MRI pixel against the admitted source mapping; freeze the 16 batches, initial model, masks and metadata into a private input bundle of at most **2 GB**. Run original loss versus proposed distributed-loss CPU checks. No held-out AUC or data-dependent selection. Private Kaggle attachment publication/version pinning is a separate preparation action; no such asset exists from this research.
2. **One private offline TPU allocation:** verify every attachment hash/version and actual runtime/topology first. Run the first three reference CPU updates in the actual Torch 2.8 host runtime before TPU workers start, separating the software-version difference from the backend difference. Do not install packages. This custom ResNet implementation does not need timm; record its installed version and avoid making it an unneeded model dependency.
3. **Continuous TPU path:** start all eight workers from the exact initial model, run the 16 fixed batches, retain step 0/3/8/16 state and prescribed training-study logits. First successful update is the cold compile/execute measurement; steps 2–16 measure steady execution. No untimed learning warmup or fresh random batch.
4. **Staged TPU path:** fresh workers start from the identical initial model, run batches 0–7, atomically publish exact step-8 state and exit. Another fresh set of workers strictly restores model, Adam, scheduler, per-rank RNG and progress/exposure sequence; execute only batches 8–15. The notebook supervisor must support these fresh worker processes inside the one consumed session. If multiple fresh PJRT launches fail in that environment, retain failure and stop; do not emulate a fresh process by reusing an initialized runtime.
5. **One CPU verification allocation:** retrieve only the bounded output archive, verify exact remote source/settings/input/runtime/terminal identity and full hashes, then load exported step-16 state strictly into the original CPU 2.7.1 model. Decode the eight prescribed original MRI studies afresh and use shared native pooling/batch-two, 16-thread inference. Verify all prescribed outputs and portable checkpoint/config/licence/provenance inventory. This is a delivery smoke check, not a Kaggle hidden submission or final candidate package.

Save ordinary CPU tensors through XLA's documented CPU-converting save path; use one designated global writer, atomic temporary-file publication, and no direct XLA tensor pickle. Preserve the complete training checkpoint content, including optimizer scalar steps/moments and all RNG/sampler identities; separately export a model-only portable packet. Use restricted `weights_only=True` loading. A diagnostic checkpoint needs its **own pilot identity**, with a reference to the registered scientific inputs; never label it a CPU Ticket 64 checkpoint or weaken that run's strict device/config identity. [Official saving guidance](https://docs.pytorch.org/xla/release/r2.8/learn/pytorch-on-xla-devices.html), [pinned CPU-converting save implementation](https://github.com/pytorch/xla/blob/d517649bdef6ab0519c30c704bde8779c8216502/torch_xla/core/xla_model.py).

## Predeclared acceptance and timing evidence

Require exact UIDs, ordering, targets/masks/descriptors, source counts, input bytes, initialization bytes and buffer identities. No skipped or duplicated update. Every real and padding rank must have finite loss/gradients/parameters and matching Adam/scheduler progress; aggregate finite guards across all ranks before updating, so a failing rank cannot leave others waiting in collectives. Stem, layers 1–4 and head must change; running buffers stay byte-identical. Compare all replica final model/optimizer hashes.

Same-backend continuous versus fresh resumed TPU states must be **tensor-exact**, including model, Adam, scheduler, progress/exposures and next sampler state. Initial CPU 2.7.1 versus CPU 2.8 logits, fresh CPU checkpoint reload and repeated native CPU source replay must meet **maximum absolute error 1e-6**. Predeclare **`rtol=1e-4, atol=1e-6`** for CPU 2.8 versus TPU initial/step-3 logits, loss, reduced gradients and Adam/model tensors, reporting per-tensor maximum errors and finite support. These proposed engineering tolerances do not establish mathematical CPU/TPU identity; any breach fails the pilot and requires diagnosis under a distinct plan, never retrospective widening. Final TPU versus its own exported CPU inference uses the same cross-backend tolerance; CPU delivery replays remain 1e-6.

Measure attachment/hash startup, initial host reference, each fresh worker startup, forward/backward and optimizer graph compilation separately, first synchronized update, each subsequent synchronized global update, input-transfer/read cost, finite-guard transfers, checkpoint CPU transfer/write/reload and original-source replay. Report max across ranks, median and maximum steady interval, peak host RSS and actual device memory metrics where supported. Explicit finite-guard/loss materializations are intentional and included in timing. Avoid copying every tensor or reading every parameter in each timed step.

Capture XLA `CompileTime`, `ExecuteTime`, transfer metrics, graph hashes and fallback counters by phase. Expected new graphs include cold forward/backward, Adam's initial state versus initialized-state update, finite guards, checkpoint/export inference and each fresh runtime. After the initialized steady graph is established, changing only image/mask values must not cause a new per-batch graph. Fail unsupported-op CPU fallback in prediction/backpropagation, rank divergence, data-dependent graph churn or unsupported memory. An absent device-memory counter is recorded as unknown, not zero. [Official XLA performance diagnosis](https://docs.pytorch.org/xla/release/r2.8/learn/troubleshoot.html).

The existing shared trainer is explicitly **CPU-scoped** for this model and uses masked indexing, CPU finite checks and loss materialization. Do not merely change `device='xla'` in a frozen Ticket 64 worker. Preparation needs a separately frozen pilot adapter implementing the same science, tensor-safe loss, distributed reduction, synchronization, RNG/state serialization and original exposure accounting, plus meaningful CPU checks. [Current CPU guard/loop](../../src/rsna_knee/training.py).

**Adam graph stability is a concrete open risk.** Torch 2.8's ordinary noncapturable Adam intentionally keeps its step scalar on CPU and computes bias corrections from a host value. Those changing scalar coefficients can enter an XLA graph as constants; measure whether they produce repeated compilation. Preserve ordinary Adam for this first fixed pilot and count compilation in the actual interval. Do not conceal it behind an untimed warmup. The pinned XLA `syncfree.Adam` falls back to ordinary Adam when `found_inf=None`; merely swapping the class would not resolve this issue. A device-tensor Adam path would need a distinct frozen operational adapter, complete moment/step/export checks and comparison to admitted Adam before adoption; it is not an automatic fallback or optimizer sweep in this request. A graph-stability failure is useful diagnosis, but does not admit full training. [Torch 2.8 Adam source](https://github.com/pytorch/pytorch/blob/v2.8.0/torch/optim/adam.py), [XLA 2.8 syncfree Adam source](https://github.com/pytorch/xla/blob/d517649bdef6ab0519c30c704bde8779c8216502/torch_xla/amp/syncfree/adam.py).
